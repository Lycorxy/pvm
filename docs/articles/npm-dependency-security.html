pnpm 依赖管理安全三部曲 —— 让项目 今天能跑 → 明天能跑

一、"在我机器上能跑" 为什么最危险

三个真实案例，看依赖是如何悄悄漂移的

案例 1

隐性版本升级

^ 符号允许装 4.x 最新版，新队友 clone 装了更新的补丁，引入了你没测过的行为。

"lodash": "^4.17.20"
案例 2

lockfile 漂移

同一个 lockfile，不同 pnpm 版本可能解析出不同的依赖树，CI 解析出不一致的子依赖。

some-sub-dep: 1.0.0
案例 3

peer dependency 地狱

版本不兼容报错还算好，更可怕的是不报错但运行时表现异常，难以定位。

peer react@"^17"

二、三步锁死，让依赖永不漂移

从工具链 → 策略 → 真相，逐层锁死

1

锁 pnpm 版本

.pvmrc

不同人用不同 pnpm，lockfile 解析结果可能不同。用 PVM 锁死版本，cd 进项目自动锁定。

pvm use pnpm@9 --local # .pvmrc → pnpm = 9.15.0
→
2

冻依赖策略

.npmrc

^ ~ * 是漂移根源。配置精确版本 + 冻结 lockfile + 自动装 peer，从策略上堵死。

save-prefix="" prefer-frozen-lockfile=true resolution-mode=time-based
→
3

正确使用 lockfile

pnpm-lock.yaml

依赖的唯一真相来源。CI 用 --frozen-lockfile 严格模式，不一致直接报错拦截上线。

pnpm install pnpm install --frozen-lockfile

三、安全三角：提交到 git 的三个文件

三者构成依赖安全的等边三角形，缺一不可

.pvmrc

锁定工具链版本
node / pnpm 版本，PVM 自动读取 → pvm use

.npmrc

锁定安装策略
精确版本 + 冻结 lockfile，堵死语义化漂移

pnpm-lock.yaml

依赖唯一真相
必须提交、禁止手编、冲突用脚本解

四、CI/CD 流水线：frozen 模式拦截漂移

lockfile 与 package.json 不一致 → 直接报错，绝不静默放行

📦 pvm use
读取 .pvmrc 锁定版本
→
📥 pnpm install
本地开发（尊重 lockfile）
→
🔒 --frozen-lockfile
CI 严格模式
→
🚫 不一致即报错
拦截上线
场景pnpm install--frozen-lockfile
lockfile 与 package.json 一致✅ 正常安装✅ 正常安装
lockfile 与 package.json 不一致⚠️ 静默更新 lockfile❌ 直接报错
某个依赖有新版本⚠️ 可能更新❌ 严格使用 lockfile 版本
适合场景本地开发CI / 生产部署
