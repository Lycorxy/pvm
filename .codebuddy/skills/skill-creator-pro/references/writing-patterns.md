## Description：3 部分公式

每个 description 必须包含三个部分：

```
[功能描述，第三人称]。当 [触发关键词] 时使用。不要用于 [反触发场景]。
```

### 正确示例

**代码评审：**
> "执行代码评审，检查 bug、安全问题。当用户请求 代码评审、review code、检查 bug、优化现有代码时使用。不要用于编写新功能、回答语法问题。"

**版本管理器：**
> "管理 AI 对话代码版本，支持快照和回滚。当用户说 保存版本、查看历史、回滚代码、对比版本时使用。不要用于 git 操作或 lint 修复。"

### 反模式

| 错误示例 | 问题 |
|---------|------|
| "帮助写代码" | 无触发词，无边界 |
| "我可以帮你评审代码" | 第一人称（破坏注入） |
| "一个处理文档的 skill" | 太模糊，无操作清晰度 |

## 输出格式模板

### 严格模板（需要确定性输出）

```markdown
始终使用此确切格式：

## [章节标题]
[具体结构 — 不得偏离]

## [章节标题]
[具体结构 — 不得偏离]
```

**适用于：** API 响应、数据转换、可解析报告。

### 灵活模板（agent 判断可提高质量）

```markdown
以下为合理默认。根据上下文调整：

## [章节标题]
[建议结构 — 按需调整]

## [章节标题]
[建议结构 — 按需调整]
```

**适用于：** 分析报告、建议、自适应输出。

## 决策树

用于有分支逻辑的工作流：

```
需要操作？
├── 条件 A → 步骤 X（确切命令）
├── 条件 B → 步骤 Y（带参数）
└── 都不满足 → 步骤 Z（默认路径）
```

**规则：**
- 每个分支都以具体步骤结束
- 无死胡同（每条路径都有结果）
- 最常见路径在前
- 嵌套最多 2 层深度

## Skill 正文清单

每个 SKILL.md 正文必须包含：

- [ ] **概述**：1-2 句话（做什么 + 为什么）
- [ ] **何时使用**：触发条件列表，含关键词
- [ ] **何时不使用**：反触发词列表
- [ ] **工作流**：编号祈使句步骤（非散文段落）
- [ ] **自由度等级标注**：如混合使用，每步标注 [低]/[中]/[高]
- [ ] **知识需求声明**：每个需要外部知识/上下文/记忆的 Step，声明数据契约
- [ ] **输出格式**：模板，标明严格/灵活
- [ ] **错误处理**：每类错误的显式恢复（非泛化的"处理错误"）
- [ ] **验证清单**：agent 必须通过的交付前检查
- [ ] **参考资料**：懒加载文件链接（仅一层深度）

### 正文长度预算

| 组件 | 建议行数 |
|------|---------|
| 概述 + 边界 | 15-20 |
| 工作流步骤 | 30-80 |
| 输出格式模板 | 10-20 |
| 错误处理 | 10-20 |
| 验证 | 5-10 |
| 参考资料链接 | 5-10 |
| **总目标** | **<200**（为领域逻辑留空间） |

如果领域逻辑导致正文 > 500 行 → 立即卸载到 references/。

## 知识需求声明与契约获取

> 完整契约规范：[contract-pattern.md](contract-pattern.md)

当某个 Step 需要 MCP 提供的知识库/上下文/记忆时，按以下标准写法声明并获取。

### Step 写法标准模板

```markdown
### Step N：[步骤名]

🔒 数据契约：{contract-id}（criticality: required | preferred）
   详见 skill.config.yaml → step-contracts

#### 契约获取子流程
按 providers 链获取 {output 字段列表}：
  1. MCP {server}:{tool}（优先，存在时必调用）
  2. 内置 {builtin strategy}（降级）
  3. fallback: {ask-user | local}（最终）
播报：✅ [Step N·契约] {contract-id} 已就绪（来源：{MCP/内置/本地/用户}）
全部失败且 on-missing=block → ⛔ 阻断，不得继续
全部失败且 on-missing=degrade → 用 {degrade-source} 兜底继续

#### 核心逻辑（消费契约数据，零 MCP 工具名）
1. [用注入的 output 数据做具体处理]
2. [带决策树的步骤（如有分支）]
3. [带验证检查点的步骤]

**播报完成：** `"✅ [Step N] …完成"`
```

### 关键规则

- **核心逻辑零 MCP 工具名**：MCP 调用只在"契约获取子流程"中出现，且格式标准化
- **核心逻辑只消费 output 字段**：不判断数据来源（MCP/内置/用户），逻辑与实现解耦
- **providers 至少两级**：mcp + builtin/fallback，保证 MCP 缺失时仍可用
- **播报来源**：契约获取后必须播报数据来源，便于追溯

### 无 MCP 需求的 Step 写法

不需要外部数据的 Step，无需契约块，直接写核心逻辑：

```markdown
### Step N：[步骤名]

[自由度标注] 执行：
1. [祈使句步骤]
2. [步骤]

**播报完成：** `"✅ [Step N] …完成"`
```

## 完整 SKILL.md 正文模板

创建新 Skill 时，直接复制此模板并填充：

```markdown
# Skill 标题

## 概述
[1-2 句话：做什么 + 为什么]

## 何时使用 / 何时不使用
[触发条件 + 反触发词]

## 🛑 入口守卫

```
本 Skill 被 use_skill 加载后，必须按顺序执行 Step 0→1→2→... 全部步骤。
每步必须播报对应完成消息。未播报的步骤 = 未执行 = 违规。

禁止行为：
  ✗ 跳过 Step 0 直接执行核心逻辑
  ✗ 不播报完成消息（无日志 = 没走流程）
  ✗ 无声跳过任何步骤

唯一例外：同会话已执行并播报过的步骤可跳过，但必须声明：
  ⏭️ [跳过] Step N — 原因 | 风险
```

## 核心工作流

### Step 0：规则注入（🔒 强制 · 最高优先级 · 不可跳过）

依据该 RULE 是否需要常驻 System Prompt 来决定注入方式：

```
需要注入的规则内容是什么？
├── 需要 alwaysApply: true？（需常驻 System Prompt，跨会话持久）
│   └── → use_skill("specflow-rules-engine")
│       1. 同步 RULE.mdc 到 .codebuddy/rules/<skill-name>（alwaysApply 生效）
│       2. 检测 System Prompt 是否已注入
│       3. 未注入 → read_file 兜底（强制 · 最后防线）
│
└── 不需要 alwaysApply: true？（仅当前会话需要）
    └── → read_file 直接注入上下文（强制 · 最后防线）
        1. 直接读取目标文件内容读入上下文
        2. 确认内容已可见（无需同步到 System Prompt）
```

> **何时用 alwaysApply？** 当该 RULE 是**领域核心约束**，每次会话都必须自动生效时（如 ESLint 规则、CSS 铁律、前后端联调约束）。
>
> **何时不用？** 当该 RULE 仅对当前 task 有用，无需永久注入 System Prompt 时。

**播报完成消息（必须逐字输出）：**

```
✅ [Step 0] 规则注入完成
  ▸ 注入方式：{specflow-rules-engine / read_file 兜底}
  ▸ alwaysApply: {true / false}
  ▸ 规则内容已就绪
```

🔒 数据契约：{contract-id}（criticality: required | preferred）  ← 有 MCP 需求时才写此块

  2. 内置 {strategy}（降级）

播报来源。全部失败 → on-missing 策略。

#### 核心逻辑（消费契约数据）
1. [祈使句步骤 — 具体操作]
2. [带决策树的步骤（如有分支）]
3. [带验证检查点的步骤]

**播报完成：** `"✅ [Step 1] …完成"`

## 中断与恢复机制

若执行过程被中断，重新继续时必须：

1. 扫描已有输出内容，检查已完成的步骤
2. 播报恢复点：
   ```
   ⏯️ [恢复] 上次进度：X/Y 步完成
   已完成：✅ Step 0 — 规则注入
   待完成：⬜ Step 1 — ...
   断点：从 Step 1 继续
   ```
3. 从断点继续，不重复不遗漏
```
