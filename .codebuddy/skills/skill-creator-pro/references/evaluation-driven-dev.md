# 评估驱动开发

构建解决**真实问题**的 skill，而非想象中的问题。

## 评估优先方法

传统方法（有缺陷）：
1. 写大量文档
2. 希望它覆盖了正确的情况
3. 后来发现它错过了重点

评估驱动方法：
1. **识别缺口** — 在无 skill 情况下运行，记录失败
2. **创建评估** — 为每个缺口构建测试场景
3. **建立基线** — 测量无 skill 时的表现
4. **编写最少指令** — 仅足够通过评估
5. **迭代** — 运行评估，与基线比较，优化

## 步骤 1：识别缺口

在编写**任何** skill 内容之前：

1. 让 Claude（不带 skill）执行代表性任务
2. 记录每一次失败、困惑或次优行为：
   - 你不得不反复提供什么上下文？
   - 它犯了什么错误？
   - 它漏掉了什么或误解了什么？
   - 它在哪里卡住或走了错误路径？

3. 分类缺口：
   - **可发现性** — 不知道要使用此方法
   - **执行** — 知道要做什么但做错了
   - **完整性** — 完成了大部分但漏掉了步骤
   - **质量** — 完成了但输出质量差

## 步骤 2：创建评估套件

创建至少 3 个评估场景。每个评估测试特定缺口：

### 评估结构

```json
{
  "id": "eval-001",
  "skill": "skill-name",
  "query": "用于测试的确切用户提示词",
  "files": ["所需测试文件列表"],
  "expected_behavior": [
    "skill 必须采取的具体操作",
    "必须产生的输出格式",
    "必须处理的边界情况"
  ],
  "forbidden_behavior": [
    "必须避免的常见错误",
    "必须不采取的错误方法",
    "必须不产生的输出"
  ],
  "gap_addressed": "此测试针对哪个已识别缺口"
}
```

### 评估示例

**评估 1 — 正常路径（基础功能）：**
```json
{
  "id": "code-review-eval-001",
  "skill": "code-review-check",
  "query": "检查此 TypeScript 文件有无 bug 和问题：src/auth/login.ts",
  "files": ["src/auth/login.ts"],
  "expected_behavior": [
    "完整读取目标文件",
    "至少识别出第 23 行的明显 SQL 注入",
    "标记 fetch 调用上缺失的错误处理",
    "输出带行号的结构化评审",
    "优先级：安全 bug > 逻辑错误 > 风格"
  ],
  "forbidden_behavior": [
    "建议重写整个文件",
    "仅评论格式/风格",
    "漏掉 SQL 注入漏洞"
  ]
}
```

**评估 2 — 边界情况（边界条件）：**
```json
{
  "id": "code-review-eval-002",
  "skill": "code-review-check",
  "query": "检查此空/近空文件：src/utils/placeholder.ts",
  "files": ["src/utils/placeholder.ts"],
  "expected_behavior": [
    "识别文件内容极少",
    "优雅报告'未发现重大问题'",
    "不捏造不存在的问题",
    "仍遵循正确输出格式"
  ],
  "forbidden_behavior": [
    "在空输入上崩溃或报错",
    "编造假问题以显得有用",
    "因"无报告内容"而跳过输出格式"
  ]
}
```

**评估 3 — 反触发（不应激活）：**
```json
{
  "id": "code-review-eval-003",
  "skill": "code-review-check",
  "query": "为我的鉴权模块写一个新的登录函数",
  "files": [],
  "expected_behavior": [
    "不激活 code-review-check skill",
    "视为代码编写请求",
    "编写新代码而非评审现有代码"
  ],
  "forbidden_behavior": [
    "激活评审模式并评审不存在的代码",
    "问"我应该评审哪个文件？"而非编写"
  ]
}
```

## 步骤 3：建立基线

对于每个评估，测量**不带** skill 时 Claude 的表现：

| 评估 ID | 测试的缺口 | 基线得分 (0-5) | 备注 |
|---------|-----------|----------------|------|
| eval-001 | 基础执行 | 2/5 | 漏掉 SQL 注入，无结构化输出 |
| eval-002 | 边界情况处理 | 1/5 | 崩溃或捏造问题 |
| eval-003 | 触发准确性 | 3/5 | 有时错误触发 |

此基线是你的"前"测量。每次改进都必须针对这些数字显示进展。

## 步骤 4：编写最少指令

仅编写足够内容以提高基线得分。从稀疏开始：

1. 起草 SKILL.md，仅含核心工作流（初始目标 <100 行）
2. 首先关注**最高影响**的缺口
3. 仅在评估显示失败时添加细节
4. 抵制 preemptively 添加"全面"覆盖的冲动

**原则：** 如果在没有特定指令的情况下评估通过了，该指令就是不必要的 token。

## 步骤 5：基于证据迭代

每次迭代后：

1. 重新运行所有评估
2. 与基线比较得分
3. 对于每个提高的得分 → 记录什么改变了
4. 对于每个不变/降低的得分 → 调查原因
5. 仅添加能推动指标的 content

### 迭代日志模板

| 迭代 | 改变了什么 | eval-001 | eval-002 | eval-003 | 假设 |
|-----------|-------------|---------|---------|---------|-----------|
| v0.1（基线） | 无 skill | 2/5 | 1/5 | 3/5 | — |
| v0.2 | 添加了 description 触发词 | 2/5 | 1/5 | 5/5 | 更好的反触发 |
| v0.3 | 添加了 SQLi 检测规则 | 4/5 | 1/5 | 5/5 | 显式检查有帮助 |
| v0.4 | 添加了空文件处理 | 4/5 | 4/5 | 5/5 | 边界情况指导有效 |

## Claude-A / Claude-B 迭代协议

Skill 精制的单一最有效方法：

### 设置
- **Claude-A**：专家模式（本次会话）— 设计和完善 skill
- **Claude-B**：测试模式（全新会话，已加载 skill）— 执行真实任务

### 流程

**第 1 轮 — 初始测试：**
1. Claude-A 基于缺口分析创建初始 skill
2. 将 skill 加载到全新 Claude-B 会话
3. 给 Claude-B 3 个真实任务（1 个正常路径，1 个边界情况，1 个复杂任务）
4. 系统记录观察

**Claude-B 观察清单：**
```
触发行为：
- [ ] Skill 在正确提示词上激活了？
- [ ] Skill 在错误提示词上避免了？
- [ ] 有任何意外激活或静默？

执行质量：
- [ ] 按顺序遵循工作流步骤？
- [ ] 在分支点正确做出决策？
- [ ] 产生了预期输出格式？
- [ ] 适当处理了错误？

内容问题：
- [ ] 哪个具体指令被漏掉了？
- [ ] 哪个部分引起了困惑？
- [ ] 它在哪里"猜测"或即兴发挥？
- [ ] 什么本可以帮助它成功？

导航：
- [ ] 按逻辑顺序读取参考文件？
- [ ] 找到了所需信息？
- [ ] 有任何它应该读取但未读取的文件？
- [ ] 有任何它不必要地读取的文件？
```

**第 2 轮 — 精制：**
1. 将观察结果附上具体引用返回给 Claude-A
2. Claude-A 用针对性修复更新 skill
3. 在相同任务上用 Claude-B 重新测试
4. 比较前后行为

**反馈格式：**
> 当我让 Claude-B "评审 auth/login.ts" 时，它：
> - 正确激活 ✅
> - 尽管我们有规则，仍漏掉了第 23 行的 SQL 注入 ❌
> - 输出格式正确，但缺失优先级列 ⚠️
>
> 假设：SQLi 规则埋在 references/ 中。我们应该将它提升到主 SKILL.md 吗？

**第 3 轮+ — 打磨：**
- 重复直到所有关键和必需问题解决
- 跟踪收益递减 — 当每轮改进 < 10% 时停止
- 将最终评估得分记录为回归测试基线

## 团队反馈集成

如果多人使用 skill：

1. 分享 skill 并让用户注意：
   - 它在预期时触发了吗？
   - 指令清晰吗？
   - 什么缺失或令人困惑？
2. 跨用户聚合反馈
3. 寻找模式（非一次性投诉）
4. 优先处理影响多个用户的变更
